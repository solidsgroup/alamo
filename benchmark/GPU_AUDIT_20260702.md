## 1. Structural facts (orientation for future audits)

- **The GPU build is an 11-file closure**, defined in `src/GPU/IntegratorPolicy.mk`.
  Only integrator `flame` is GPU-supported. Sources: `BC/BC.cpp`,
  `BC/Constant.cpp`, `IO/FileNameParse.cpp`, `IO/ParmParse.cpp`,
  `IO/WriteMetaData.cpp`, `Integrator/Flame.cpp`, `Integrator/Integrator.cpp`,
  `Operator/Elastic.cpp`, `Operator/Operator.cpp`, `Set/Set.cpp`,
  `Util/Util.cpp`, entry `src/alamo_gpu.cc`. Everything else in `src/` is
  CPU-only dead weight with respect to the GPU binary — it cannot fault on
  device *today*, but see §3 for what breaks if it is ever pulled in.
- **All CPU/GPU divergence (~40 sites) is gated on the project-private macro
  `ALAMO_GPU`** (defined by `configure` on the nvcc line, `configure:802/808`)
  — **not** the AMReX-standard `AMREX_USE_CUDA`/`AMREX_USE_GPU` (zero hits in
  `src/`). Any future audit or grep sweep that searches for the standard
  AMReX macros will silently miss every ALAMO-side GPU branch. Search for
  `ALAMO_GPU` instead.

## 2. Fixed live defect — `DeviceErrorFlag` read-back raced the stream pool

**Status: fixed 2026-07-02.** The audit originally recorded this as a
production-affecting action item; the fix landed in `Util::AbortIfDeviceError`
so all call sites share the same full-stream-pool read-back barrier.

`DeviceErrorFlag::value()` (`src/Util/Util.H:68-78`) calls AMReX's
`DeviceScalar::dataValue()`, which does a `Gpu::dtoh_memcpy` followed by
`Device::streamSynchronize()`. That sync is **current-stream-only**
(`ext/AMReX-Codes/amrex/Src/Base/AMReX_GpuDevice.cpp:856-866`). AMReX's
`MFIter`, however, cycles boxes across a **pool** of CUDA streams — the exact
same mechanism responsible for the historical `interpolation()` `tmpfab`
use-after-free (see `benchmark/archive/elixir_race_audit.md`).

Consequence: `SetDeviceError` writes (`Util.H:80-86`, atomic —
`Gpu::Atomic::AddNoRet`) from boxes processed on streams *other than* the one
active when the MFIter loop exits may still be in flight when
`AbortIfDeviceError` reads the flag right after the loop:

- `src/Solver/Nonlocal/Newton.H:121-124` and `:228-231`
  (`Newton::prepareForSolve`, **unconditionally compiled** in `ALAMO_GPU`
  builds — always live in production)
- `src/Operator/Elastic.cpp:675` (`Fapply`, `AMREX_DEBUG`-gated)
- `src/Operator/Elastic.cpp:889` (`Diagonal`, `AMREX_DEBUG`-gated)

Because the writes are atomic, there is no memory corruption — the failure
mode is a **silent false negative**: a NaN / invalid-`kinvar` error raised by
a non-last-streamed box goes undetected on any multi-box run. Single-box runs
(most local smoke tests) cannot exhibit this, which is why it has not
surfaced in the existing GPU test suite (`tests/GPU/`, 9/9 green — see
`benchmark/archive/GPU_TEST_SUITE_FIXES.md`).

**Fix applied:** `amrex::Gpu::streamSynchronizeAll()` before the flag read — the same
idiom already used for the `dsol_mf` UAF fix at `Newton.H:459`. Cleanest
placement is inside `Util::AbortIfDeviceError` itself (`Util.H:148-151`), so
every one of the four call sites is covered by one edit. Cost: one full-device
sync per `prepareForSolve`/diagonal check (i.e. once per Newton iteration) —
negligible relative to the Newton solve itself.

The same closure also added a full-device sync at
`Base::Mechanics::TimeStepBegin` before local `elastic_op` destruction. That
closes the broader AMR/MG operator-buffer lifetime race that can otherwise
reuse `elastic_op` storage while a straggler MLMG kernel is still writing.

Post-fix validation:

- `compute-sanitizer` on the failing `centre_bore_3d_128_a2` path ended with
  `ERROR SUMMARY: 0 errors`.
- Five consecutive `gpu_strict centre_bore_3d_128_a2` harness runs completed:
  `20260702T173824Z`, `20260702T174203Z`, `20260702T174540Z`,
  `20260702T174914Z`, `20260702T175249Z`.
- A scan of those five bundle logs found no CUDA illegal access, segfault,
  abort, or error strings.

**This is the same bug class** as the elixir UAF and the traction-diagnostic
race (`benchmark/SUCCESS_BOOK.md` Appendix B) — a device async-lifetime
assumption violated by the MFIter stream pool. It belongs in the async-lifetime
audit family (`GPU_ROADMAP_V3.md` task 4.B).

## 3. Dormant landmines — inert today, crash/build-break if the GPU closure is ever extended

None of these affect the current `flame`-only GPU binary. They are recorded so
a future agent extending `IntegratorPolicy.mk` or adding a solid model to a
GPU-eligible integrator does not rediscover them the hard way (i.e. via a NOVA
crash log).

1. **`PhaseFieldMicrostructure::Integrate`**
   (`src/Integrator/PhaseFieldMicrostructure.cpp:449-483`) accumulates host
   members (`volume`, `area`, `gbenergy`, `realgbenergy`, `regenergy` —
   declared `PhaseFieldMicrostructure.H:403-407`) with `+=` directly inside an
   `amrex::ParallelFor [=] AMREX_GPU_DEVICE` lambda via implicit `this`
   capture. This is the **exact pre-fix pattern** that caused CUDA error 700
   in `Base::Mechanics::Integrate` (fixed 2026-06-26 with `ReduceOps` — see
   `docs/llm/changelog/2026-06-26-3d-elastic-gpu-fix.md` and
   `benchmark/SUCCESS_BOOK.md` Appendix B). It is also a data race even where
   local HMM masks the device fault (`benchmark/LOCAL_A100_SPOOFING.md`).
   Inert today because `alamo_gpu.cc` never instantiates
   `PhaseFieldMicrostructure`. **If this integrator is ever added to
   `ALAMO_GPU_SUPPORTED_INTEGRATORS`, port the `ReduceOps` fix first.**

2. **Missing `AMREX_GPU_HOST_DEVICE` on solid-model `W`/`DW`/`DDW`.** Every
   solid model *except* `Finite::NeoHookean` / `Finite::NeoHookeanPredeformed`
   lacks the device annotation on `W`/`DW`/`DDW`:
   `Linear::Isotropic`/`Cubic`/`Hexagonal`/`Laplacian`, `Affine::*`,
   `Finite::CrystalPlastic`, `Finite::PseudoAffine::Cubic`,
   `Finite::PseudoLinear::Cubic`. Dispatch is static name-hiding
   (`Solid.H:40-43`, "de-virtualized for GPU"), so an un-annotated derived
   `W`/`DW`/`DDW` **silently shadows** the annotated base rather than failing
   to compile at the call site — any future GPU instantiation of one of these
   models fails to compile (or, worse, resolves to the wrong overload) only at
   the point of use. `NeoHookean.H:76-79,133-135` documents a real prior
   device bug in this family (a chained Eigen `F.inverse().transpose()`
   expression template faulted on device; fixed by materializing the inverse
   first) — that fix's *recipe* is the template to follow when porting any of
   the un-annotated models.

3. **`Operator/Diagonal.cpp`**: host-style fab element access in raw nested
   loops — no `ParallelFor`, no `elixir()`, no tiling, no device-safety
   concept at all. Not part of the GPU closure (`Elastic`'s own `Diagonal` in
   `Elastic.cpp` is the one actually used on device). Flagged only so it is
   not mistaken for GPU-ready if ever wired in.

## 4. CI gap — GPU regressions have no automated tripwire

`.github/workflows/chamber-gpu-correctness.yml` defines `golden-gpu` and
`phase1-budget-gate` jobs, but both are gated on a `has-cuda-runner` repo
topic that is **not wired up** anywhere (no such topic is set on the repo, no
self-hosted runner is registered under it). Only the `golden-cpu` leg actually
executes on every push. In practice this means:

- No CI signal exists for GPU build breakage, GPU-only device faults, or
  Phase 1 physics-budget regressions.
- The gap is silent — the workflow reports green because the CPU leg passes,
  not because the GPU legs ran and passed.

This is the CI half of `GPU_ROADMAP_V3.md` task 1.F (which already documents
the job as "gated, non-blocking... `[self-hosted, cuda]` runner, prints
`skipped: no GPU` otherwise" as the target state) and task 2.D (locking the
perf-regression job in). The audit's contribution is confirming the *current*
state is not even skip-safe-and-visible — it is silently absent. Wiring the
`has-cuda-runner` topic (or switching the `runs-on:` selector to the
documented `[self-hosted, cuda]` label directly) is a prerequisite for both
tasks to mean what they say.

## 5. Fapply perf anatomy — supporting evidence for Phase 3 / the C1 edits

Phase-A profiling already established `Operator::Elastic::Fapply` = 74.6% of
GPU kernel time at ~255 registers/thread (~12.5% occupancy) —
`benchmark/archive/PHASE_A_FINDINGS.md`. This audit read the kernel itself to
identify *why*, which is direct supporting evidence for the register edits
already staged on `chamber-gpu-elastic-opt` (`GPU_ROADMAP_V3.md` task 3.A) and
for ordering the remaining Phase 3 tasks:

- **Dominant register-pressure driver: `grad(C)` at `Elastic.cpp:615-624`.**
  Three `Set::Matrix4<3,MajorMinor>` temporaries (21 doubles each = 63 doubles
  live simultaneously) are built via centered-difference
  `Numeric::Stencil<MATRIX4,...>::D` calls — 6 full 168-byte tensor loads from
  global memory plus ~126 flops per cell. The `if (!m_uniform)` guard that
  wraps this **never actually skips it**: `Base/Mechanics.H:198` calls
  `SetUniform(false)` unconditionally, so the branch is always live for
  chamber sims. **This is exactly what the C1 branch's "grad(C) one-`Matrix4`-
  at-a-time" edit targets** — confirms 3.A is attacking the real hotspot, not
  a secondary one.
- **`DDW(i,j,k)` (21 doubles) is loaded from global memory twice per cell**
  when psi is active: once at `Elastic.cpp:613`
  (`f = (DDW(i,j,k)*gradgradu)*psi_avg`) and again at `Elastic.cpp:629`
  (`f += (DDW(i,j,k)*gradu)*gradpsi`). A cached local eliminates a redundant
  168-byte load. Not yet in any staged edit — candidate addition to 3.A or 3.B.
- **Boundary handling lives inside the main kernel**
  (`Elastic.cpp:537-670`, `if (xmax||xmin||...)` evaluated per thread): warp
  divergence plus every interior thread reserves registers for the BC-eval
  path regardless of whether it needs it. The C1 branch's "boundary
  `sig`-sink" edit partially addresses this; task **3.B** (interior/boundary
  kernel separation) is the stronger, fuller form of the same idea — this
  finding is direct motivation for 3.B, not just 3.A.
- **Zero `__launch_bounds__` anywhere in `src/`** — confirms the lever is
  still fully open (already tracked as deferred; see task 3.F).
- **Already-good, no action needed:** the hot tensor contractions
  (`DDW*gradu` / `DDW*gradgradu`) route through hand-unrolled friend
  `operator*` overloads (`Matrix4_MajorMinor.H:692-707,726-780`) indexing
  `data[]` directly — not the branchy bounds-checked `operator()(i,j,k,l)`; no
  virtual/indirect calls anywhere in the hot lambda; the per-cell model struct
  is small (~88 bytes for `NeoHookeanPredeformed`); `Homogenize` hoists
  pressure constants into `set_pressure()` (host-side, not recomputed
  per-cell).

### Secondary perf (informational — no task currently gated on these)

- **`Fsmooth`** (`Operator.cpp:350-417`): 2 Jacobi sub-iterations, each = 1
  `Fapply` launch + 3 `MultiFab` op launches + one `ParallelFor` **per
  component** (DIM extra launches) + `FillBoundary`/nodalSync → 16+ kernel
  launches per `Fsmooth` call in 3D. Easy, uncontroversial win: collapse the
  per-component `ParallelFor` into a single launch. Not yet a numbered Phase 3
  task — candidate for folding into 3.A or a new task if it's worth its own
  A/B.
- **Line-search** (`elastic.solver.line_search`, GPU-hardened implementation
  present in `Newton.H:389-459`, default `false`): up to `nlev × DIM × 9` `MultiFab::norm0` device-reduction +
  host-sync round-trips per Newton iteration when enabled. Inherent to
  backtracking, not a bug — but a real profiling caveat for anyone who
  benchmarks with `line_search=1` on. Its `dsol_mf` UAF is correctly fixed by
  `streamSynchronizeAll` at `Newton.H:459` (see `docs/llm` memory
  `cpu-newton-damping` for the line-search feature's own history).
- The 3 explicit `streamSynchronize` sites in the GPU closure
  (`Util/BMP.H:62`, `IC/StarAftGrain.H:358`, `Newton.H:459`) are all
  correctness-required staging/UAF syncs, one per solve/IC-load, not per-cell
  — no gratuitous syncs found anywhere in the closure.
- Host `MultiFab` reductions in `Operator.cpp` (norminf/min/max at `:56,78,
  82-83,131-132`) are all behind opt-in diagnostic flags, not unconditional.

## 6. Verified clean (re-confirmed, no action needed)

Each item below was checked directly in code, not assumed from prior docs:

- `interpolation()` `tmpfab.elixir()` (`Operator.cpp:728`) with its
  explanatory comment — still present, still the fix.
- `ReduceOps` pattern in `Base::Mechanics::Integrate`
  (`Mechanics.H:437-534`), `Flame::Integrate` (`Flame.cpp:1051-1073`),
  `Flame::TimeStepComplete`'s fused 5-way reduction (`Flame.cpp:608-654`).
- `streamSynchronizeAll` in `Mechanics::TimeStepBegin`
  (`Mechanics.H:215-225`, the MLMG-buffer UAF fix) and `Newton::solve`
  (`Newton.H:459`).
- `Newton::prepareForSolve`'s old CUDA 719/700 crash pattern is fully
  replaced by the `DeviceErrorFlag` machinery (which itself has the race
  documented in §2 above — the *crash* is fixed, the *detection* has a gap).
  `DX` is captured as `Set::Vector` locals; BCs go through static
  `AMREX_GPU_HOST_DEVICE eval()` (de-virtualized).
- `ALAMO_GPU_UNSUPPORTED_HOST_LOOP` (`Util.H:29-36`) hard-refuses all 7
  host-loop ICs/BCs at parse/init time: `PointList`, `PNG`, `PSRead`,
  `Laminate`, `Trig` (×2), Expression-vector, plus
  `BC::Operator::Elastic::Expression::Init` (×2).
- `elastic.type=dynamic` is refused at parse time under `ALAMO_GPU`
  (`Mechanics.H:58-61`) — its kernel would dereference a host BC pointer on
  device.
- No `[&]` capture reaches a device lambda anywhere in `src/` (the 7 non-test
  hits are all host-only). No `Eigen::Dynamic` anywhere in `src/`. Tiling
  policy is consistent (`TilingIfNotGPU` everywhere it matters). `Set::Matrix4`
  is hand-written fixed-size (not Eigen), every op
  `AMREX_GPU_HOST_DEVICE FORCE_INLINE`. The `Integrator::Restart` OOB fix and
  the headerless-`thermo.dat` fix are both still present
  (`Integrator.cpp:750-759` / `:1290-1306`). `Util::BMP` and `StarAftGrain`
  correctly stage host data into `Gpu::DeviceVector` before any device use.
- `tests/GPU/` = 9 tests (C1-C4, F1-F2, P1-P3), all passing per the prior
  session (`benchmark/archive/GPU_TEST_SUITE_FIXES.md`).
